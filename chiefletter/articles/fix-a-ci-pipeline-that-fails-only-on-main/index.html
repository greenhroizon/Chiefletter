Fix a CI Pipeline That Fails Only on Main

Trace main-only build failures through branch differences, flaky tests, secrets, and environment drift with a repeatable debugging plan.

Capture the failure before changing the workflow

A failure that appears only on the main branch feels mysterious because the code may look identical to the code that passed on a pull request. Start with evidence. Save the job URL, commit SHA, runner image, workflow revision, failed command, and the first useful error above the stack trace. Record whether it happens on every run or only sometimes. “CI is red” is a symptom. The command and its inputs tell you where to investigate.

Compare the exact commit that failed with the last successful commit. A merge commit can contain target-branch changes that were absent from a feature branch run. Check whether the pull request workflow tested a merge result or only the contributor branch. Also check whether the workflow file itself changed. A different trigger, permission, cache key, or environment variable can alter execution even when application code is unchanged.

Compare the two execution paths

Make a short table of what differs between the passing and failing jobs: event type, branch, permissions, runner, dependency cache, secrets, concurrency, and test command. CI providers often expose a pull request event with a restricted token or omit secrets from forks. A deployment step may fail on a pull request by design, while a test step should still run without credentials. Separate the expected permission boundary from a broken test.

Read the workflow conditions line by line. Confirm that each job checks out the intended commit and uses the same runtime version. A cache restore can hide a missing install step on one path. Do not clear every cache at once. First compare the key and logs, then invalidate only the suspect entry so the next run answers a specific question.

Check for tests that depend on order or shared state

A test suite that passes alone and fails in the full job often shares state. A test may leave a database row, file, environment variable, mock, or clock override behind. Run the smallest failing test repeatedly, then run it after the test that precedes it in CI. If order matters, isolate setup and cleanup in the test harness. Use unique fixtures and remove temporary resources even when an assertion fails.

Parallel execution creates another common difference. Two tests may write to the same filename, account, port, or database schema. Re-run the suite with parallelism disabled as a diagnostic, then identify the shared resource before changing the permanent worker count. A slower serial suite is not a sound final fix if a test still relies on hidden ordering. Make resource ownership explicit so parallel runs remain safe.

Test timing and external dependencies

A test that calls a live service, public package registry, or real clock can pass locally and fail under CI load. Look for fixed sleeps, short timeouts, rate limits, and assumptions about network availability. Replace timing guesses with an observable condition, such as waiting for a request to finish within a bounded timeout. For application behavior, prefer a controlled local server or recorded fixture over a third-party dependency.

If only a few failures occur, calculate the rate from actual runs rather than calling the suite flaky by instinct. Save the test name and failure signature for each run. A retry can gather evidence, but it should not turn a red signal green without recording the first failure. Retries also hide intermittent defects when the same timing condition exists in production. Fix the condition or quarantine the test with an owner and review date.

Look for missing credentials and unsafe assumptions

A protected secret may be available on a trusted push and withheld from an external pull request. That is a security control, not a reason to make the secret public. Split validation from deployment: run compilation and tests without credentials, then run publishing only for an approved event and protected branch. Give the publishing token the smallest required permissions. Confirm logs do not print environment values or commands containing credentials.

Do not solve a missing-secret error by adding a fake value that happens to pass one check. If a test needs a credential, provide a dedicated test credential through the provider secret store and rotate it if exposed. Better still, use a stub for unit tests and reserve a narrow integration test for a controlled environment. Explain which checks need protected credentials so contributors know what a skipped job means.

Reproduce with the same inputs, then change one thing

Use the failed SHA and the same runtime, command, and environment to reproduce the issue. If the CI runner is not available locally, use a container or local workflow runner only when it matches the job closely enough to answer the question. Keep a note of each experiment: hypothesis, one change, result. Changing a dependency, runner, cache, and timeout together may produce a green run, but it does not show which fault you fixed.

When a workflow uses a floating runner image, operating system packages can change between runs. Pin a runtime version and install required system packages explicitly. Pinning every action to an immutable revision can improve supply-chain control, but plan updates so old actions do not remain unpatched. Aim for a reproducible environment with an intentional update path, not a frozen runner no one owns.

Make the next failure easier to diagnose

Once the build passes, keep useful context in the job summary: commit, runtime, test command, and artifact links. Upload logs or reports on failure, while excluding secrets and private test data. Name workflow steps after what they verify instead of generic labels. A teammate should see whether installation, lint, tests, or packaging failed without opening every collapsed log group.

Add a regression test for the cause you found. If a main-only condition exposed a missing permission, test the workflow logic or document the protected boundary. If tests shared a fixture, isolate the data. If runner drift caused the failure, pin the relevant version and schedule an update. Close the issue with the cause and supporting evidence. That record gives the next person a starting point instead of another round of guesswork.

A practical incident note should separate the trigger from the root cause. Write: “The push workflow started failing after the merge,” then record the failed step and the exact configuration difference you found. Avoid “the merge broke CI” unless the merge itself is the cause. Share the first reliable reproduction and the repair in the pull request or runbook. This gives the team a reusable explanation and helps the next person decide whether a new red build matches the old failure or needs fresh investigation.

Frequently asked questions

Why does CI pass on a pull request but fail after merge?

The merge commit may include target-branch changes, or the push workflow may use different permissions, secrets, runner settings, or conditions. Compare the exact SHA and job configuration first.

Should I add retries to a flaky test?

Use retries to gather evidence, not hide failures. Find the shared state, timing, or external dependency and fix it. If a test must be quarantined, assign an owner and review date.

Why are secrets missing from a pull request job?

Many CI providers withhold protected secrets from untrusted fork events. Keep tests that do not need credentials separate from deploy or integration jobs that do.

How do I debug CI without reproducing it locally?

Use the failed commit, logs, runner details, artifacts, and workflow revision. Change one variable at a time and make the next run answer one clear hypothesis.

Should I pin CI runner versions?

Pin runtimes and important dependencies when reproducibility requires them, then schedule updates. A pin without an update owner can leave a project on unsupported software.

Write API Errors That Help Without Leaking Secrets

Create API error responses that guide client developers, support retries safely, and keep internal details and user data private.

Separate the client message from diagnostic detail

An API error has two audiences. The client needs a stable description of what it can do next. The operator needs enough context to investigate. Those needs should not share one unfiltered string. A database exception might help an engineer while exposing table names, query fragments, internal hosts, or personal data to a caller. Return a concise public error and keep the stack trace in restricted server logs linked by a request ID.

List the failures clients can act on: invalid input, missing permission, a resource that does not exist, a rate limit, or a temporary service problem. Give each a stable code and a plain description. Keep wording consistent across endpoints so client teams do not parse sentences that change during a copy edit. A field such as a machine-readable error code is more reliable than asking an app to search an English message for a word.

Choose a response shape and keep it stable

Use a documented error envelope with fields such as a machine-readable code, a human-readable message, an optional field-error list, and a request identifier. The exact format depends on your existing API contract or standard. Avoid returning a different JSON shape for each controller. Clients should know where to find the code and how to handle an absent optional field. Version changes to the error contract with the same care as successful responses.

For a validation failure, point to the field and the rule the client can fix. Say that a start date must be earlier than an end date, rather than returning “bad request.” Do not echo the submitted value if it might include a password, token, or private data. A client can show an actionable hint while the server keeps the rejected value out of logs. Test messages with long, malformed, and unexpected input.

Let the status code describe the protocol outcome

Use HTTP status codes consistently. A 400 response should indicate a request problem the client can correct. A 401 response means authentication is required or failed. A 403 response indicates the server understood the request but will not authorize it. A 404 can be appropriate when a resource is absent, and some services use it to avoid confirming a protected resource exists. A 429 communicates rate limiting. Document service-specific choices instead of assuming every team uses them identically.

A 5xx response should not tell a client to repeat a non-idempotent action without safeguards. If a request might have completed before the connection failed, a blind retry can duplicate a payment or create two records. For retryable failures, use documented guidance such as a Retry-After value where appropriate, and explain how idempotency keys work. Clients need to know which errors are safe to retry and which require checking the result first.

Give clients a safe next step

A useful error answers three questions: what failed, whether the client should change the request, and whether another attempt is reasonable. “Try again later” is too broad if the request is malformed. “The request limit was reached; wait before sending another request” gives the client a practical step. For a temporary server failure, state that the operation may have an unknown outcome when the system cannot confirm whether it completed.

Do not promise a retry will succeed unless the system can support that claim. A timeout may happen before the server receives the request, while a dropped response may happen after the server commits it. Design APIs with idempotency or a status lookup for actions where duplicates are harmful. The error contract should link to the relevant behavior in developer documentation, not send customers to a generic search page.

Log enough to diagnose without collecting everything

Attach a request ID to the response and corresponding server logs. Keep the identifier random or otherwise non-sensitive, and avoid using an email address or account number as a correlation key. Log the route, timestamp, service version, safe error category, and trace details your team needs. Restrict access, define retention, and avoid dumping request bodies by default. Debugging convenience is not a reason to store credentials or customer content indefinitely.

When investigating, use a redacted reproduction or synthetic data where possible. If exact input matters, remove tokens, personal identifiers, and unrelated fields before sharing it in a ticket. Ensure error reporting tools do not capture passwords, authorization headers, or query parameters with secrets. Add a test that sends a sensitive-looking value and confirms it does not appear in public errors or expected logs.

Design errors for localization and accessibility

Keep the machine code separate from display text so a client can localize a message without changing API logic. Return field identifiers that the client can associate with visible labels, and do not rely on color alone to show an error. A web form should announce a summary when appropriate, then identify the specific field and how to fix it. The API provides structured facts; the client chooses how to present them accessibly.

Avoid embedding HTML in error messages. Treat every message as text, and escape it in the client. If the API returns a detailed list, cap its size and validate each field name. Unexpected server text should never flow directly into a page. Keep examples in the API documentation aligned with the responses clients actually receive.

Test the contract from both sides

Write contract checks for status, content type, required envelope fields, stable codes, and the absence of stack traces. Include invalid input, an unauthorized request, a rate limit, and a temporary server failure. Test the client too: does it show a useful message, preserve user input when safe, and avoid retrying an unsafe operation? Snapshot tests can freeze a bad message, so review the expected behavior instead of treating a stored string as proof.

Finally, examine errors from the perspective of support. Can a teammate find the request ID, identify the service version, and see the failure category without asking for a screenshot of private data? A well-designed error reduces duplicate tickets because the person can take the next step. It also gives operators evidence without turning every response into a leak of internal implementation. Keep the contract short, document unusual cases, and update clients when behavior changes.

Keep a small compatibility table for client teams: status, stable code, whether the request is safe to retry, and the action expected from the caller. Review it when adding a new error. If a client has older behavior, introduce the new code without changing the meaning of an existing one. A change from “retry later” to “do not retry” can create duplicate work even when the JSON shape stays the same. Treat error semantics as part of the public API contract and mention the change in release notes.

Frequently asked questions

Should API errors include stack traces?

No. Keep traces in restricted server logs. Return a stable code, a safe message, and a request identifier clients can share with support.

When should a client retry an API error?

Retry only when the error and operation are safe to retry. Respect backoff guidance and use idempotency or status checks for actions that could run twice.

Should errors reveal whether an account exists?

Avoid revealing account existence when it is sensitive. Use consistent public responses and keep diagnostic detail behind access controls.

What belongs in a validation error?

Return a stable code and the field plus a rule the client can fix. Do not echo secrets or entire submitted values.

How do request IDs help support?

A request ID links a response to restricted server logs without placing personal data in the identifier itself.

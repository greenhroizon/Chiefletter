Write a Pull Request Description Reviewers Can Use

Help reviewers understand a code change with a short summary, clear test evidence, screenshots where useful, and known risks.

BY THE CHIEFLETTER EDITORIAL DESK  ·  November 21, 2026  ·  8 MIN READ

Lead with the change and the reason

Start with two things: what changed and why. “Adds a retry limit to report exports so a temporary network error does not lose the user’s request” gives a reviewer a useful frame. A title such as “Fix export” does not. Link the issue or request when one exists, but do not make the reviewer open three tabs to learn the basic purpose.

Keep the summary factual. Mention the user or system behavior that changes. If the pull request is internal refactoring with no visible change, say what structure changed and what behavior should stay the same. A clear first paragraph helps reviewers decide what context they need before reading the diff.

Show the path through the change

A short list of the main changes gives reviewers a route through the files. Group related work, such as API handling, validation, and tests. Call out a non-obvious decision or a trade-off. Do not list every changed filename if the diff already makes that easy to see. Explain what took thought.

If you tried one approach and changed it, say why. Perhaps a shared component created an unwanted dependency, so you kept the behavior local. This context is not an excuse for a complicated diff. It helps a reviewer check whether the choice fits the project and spot a missing consequence.

Give test evidence that means something

List the checks you ran and what they covered. “Unit tests pass” is less helpful than “Added cases for an empty report and a timeout. Ran the export tests and the full check suite.” If a check did not run, state why and what risk remains. Never claim a test passed if you did not run it.

For a user interface change, add a screenshot or short recording when it helps show the before and after. Include the screen size and state if those details matter. For a backend change, a sample request and response may be more useful. Remove credentials, customer information, and private URLs from the evidence.

Tell reviewers where to focus

If a decision needs special attention, ask a direct question and point to the relevant file or behavior. “Please check whether this fallback matches our retention rule” gives a reviewer a specific task. Avoid assigning reviewers a large unbounded request such as “thoughts?” when you need approval on one requirement.

Mention dependencies, migration steps, configuration changes, or rollout needs. If the change touches permissions or user data, say how you checked those paths. Reviewers should not have to infer operational consequences from a small line in a config diff.

Keep the request reviewable

A concise description cannot rescue an oversized change. Split independent work when each piece can be understood on its own. If the change must stay together, explain the dependency and organize the commits or files so the reviewer can follow them. Remove debug code and unrelated formatting changes that make the important edits harder to see.

Before requesting review, read the description beside the diff. Does it match what the code now does? Do the linked issue and test results reflect the final version? Update the description after significant changes. A stale summary creates doubt even when the implementation is sound.

Use a simple description template

Try: “Purpose” for the user problem, “Changes” for the few key decisions, “Checks” for the tests and manual review, and “Review focus” for the question you need answered. Add screenshots, migration notes, or a rollback detail when they apply. Delete headings that would contain no useful information.

A good request respects reviewer time and helps future maintainers understand why the code changed. It does not need polished marketing language. Write it as if a teammate will return to it six months later after a bug report, when the reason for the change is no longer obvious.

Frequently asked questions

What should a pull request description include?

Purpose, key changes, test evidence, review questions, and any operational or user impact. Add screenshots when they clarify a visual change.

How long should a pull request description be?

Long enough to explain the intent and checks, short enough to scan. Focus on decisions a reviewer cannot infer from the diff.

Should I include screenshots?

Include them for visual changes when they help compare states. Remove private data and note the viewport or test state if needed.

What if I did not run the full test suite?

State which checks you ran, which you skipped, and why. Describe any risk the reviewer should consider.

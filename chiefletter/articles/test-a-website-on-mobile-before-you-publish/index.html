Test a Website on Mobile Before You Publish

A repeatable mobile review for navigation, text, forms, images, and touch controls, with checks you can do before every release.

Start with the viewport people use

Check the page at 320 to 390 pixels wide, then at a larger phone width and a tablet size. Use browser developer tools for quick checks, but test on a physical phone before publishing when possible. A real device reveals touch behavior, browser bars, keyboard changes, and network delays that a desktop simulation may miss.

Look for horizontal scrolling first. It often points to a fixed-width element, long URL, unbroken word, oversized image, or layout column that refuses to shrink. Fix the cause instead of hiding overflow across the whole page. Hidden content can make a control unreachable and leave a quiet bug behind.

Check portrait and landscape orientation on pages with fixed headers, tables, or charts. Rotate the device and confirm content stays available. A layout that only works at one width may trap a visitor when the browser window changes. If a wide table needs horizontal scrolling, label the region and make the scroll area usable by touch and keyboard.

Read the page at normal size

Open the page with default text size. Check headings, paragraphs, labels, and metadata. Text should wrap without covering buttons or creating one-word columns. Increase browser zoom and use the phone’s larger text setting. A layout should respond to a reader’s choice instead of forcing tiny type to keep a desktop design intact.

Review line length and spacing as well as font size. A paragraph stretched across a narrow screen is tiring to follow. Keep comfortable margins, clear section breaks, and enough room around links. If a page is long, make the table of contents easy to reach and make jump links land below the sticky header.

Test links and buttons with the browser zoomed to 200 percent. Confirm focus remains visible and the page does not cover content with a sticky banner. Read the page at a larger text size if the device offers the setting. These checks often expose fixed heights and absolute positioning that a normal screenshot hides.

Tap every control with a thumb

Try the menu, filters, search field, article links, accordions, and form buttons. Check that the active area matches what the control looks like. Small text links packed close together cause mistakes. Give controls room and use clear focus or pressed states so the response is visible.

Open the software keyboard in every text field. Confirm it does not cover the submit button or the message explaining an error. Test the back button and any menu that opens over content. A control that works only when a mouse hovers over it is not ready for phones or tablets.

Try a slow connection with image loading disabled. The page should still explain what each image or control is for. Use dimensions or aspect ratios so late-loading images do not push the text around. If a script fails, core navigation and contact details should remain reachable wherever the page design allows.

Check images, media, and page weight

Confirm images fit their containers and keep the intended subject in view. Portrait crops can cut out the important part when a desktop landscape image is reused. Check captions and alternative text. If a video is embedded, verify the frame fits the screen and offer a direct link or transcript when the embed is unavailable.

Use the browser’s network tools or a slower connection to notice heavy images and scripts. A page should show useful content before every decoration has loaded. Compress large images and remove files the page does not need. Test a reload on a mobile connection rather than assuming every visitor has fast Wi-Fi.

Record real defects with a short screen recording, device model, browser version, page address, and steps. A report such as “menu broken” leaves too much guesswork. “At 320 pixels wide, open Topics, tap Career, then use Back. The menu covers the first heading” gives someone a reliable route to the issue.

Try the task from the beginning

Ask a person who did not build the page to complete one task on their phone. Give them a goal, such as finding the privacy policy or sending a message. Stay quiet and note where they pause, tap the wrong thing, or expect feedback. Do not explain the interface until the task ends.

Repeat the task after you fix the biggest problem. A short observation often finds issues a checklist misses, such as an unclear label or a menu that closes before a selection is made. Ask permission before recording a person’s screen, and do not capture private information in a test.

Check browser behavior for the features the page depends on. Confirm search, menus, and form validation in the main browsers your visitors use. If an older browser lacks a feature, provide a usable fallback or state the support limit. Do not test only one current phone and assume every browser draws the page the same way.

Keep a release checklist with the site

Record the page, device, browser, viewport, task, and result. Recheck high-traffic pages after changes to navigation, typography, or shared components. Fix blocked actions and clipped content before polishing minor spacing. Then run the same short route again so you know the fix did not break another part of the page.

A practical pre-release pass covers the home page, one article, one legal page, navigation, search, contact, keyboard use, and zoom. Add the site’s own important workflows. Keep the checklist short enough that someone will use it each time.

Check motion and animation settings too. A carousel or entrance animation should not hide content from someone who requests reduced motion. Pause moving content when controls appear. If a motion effect carries meaning, provide the same information in text. A quiet page is easier to use when someone is reading, zooming, or switching between tasks.

Frequently asked questions

Is browser developer tools enough for mobile testing?

They help check viewport layouts, but a physical phone catches touch, keyboard, browser, and network behavior. Use both when possible.

What phone width should I test?

Include a narrow viewport around 320 pixels, common phone widths around 360 to 390 pixels, and a tablet size. Also test browser zoom.

How do I find horizontal overflow?

Scroll sideways and inspect elements wider than the viewport. Check fixed widths, images, long text, and grids before applying an overflow rule.

What should I test first on mobile?

Navigation, the main task, text readability, forms, and any control needed to contact you or reach important information.
